# 死斗弹劾组长功能实施计划

## 一、规则定版（按你的四个答复）

- **发起**：仅进行中（RUNNING）死斗；发起人必须是正式成员（不含已退出/已移除）且不是组长；原因必填、≤20字
- **投票**：组员（含组长）对进行中的弹劾投「弹劾/维持」其一，**一票定死不可改**；发起人创建时自动记1张弹劾票；组长只能投维持（不能发起）
- **成功条件**：弹劾票 **严格大于** 当前正式成员数（含组长与发起人，不含已退出/已移除，即 `duel.member_count`）的一半；未投票视为支持组长
- **期限**：发起后24小时，到期未过半自动失败；由定时任务结算 + 详情访问/投票时惰性兜底
- **成功效果**：发起人立即成为新组长，老组长自动降为普通成员（角色由 `duel.leader_id` 派生，无需改成员行）；**不涉及任何资金变动**
- **冷却**：弹劾**失败**后 `finish_time + 24小时` 内该死斗不能再发起新弹劾；成功后不冷却（可立即弹劾新组长）
- **并发保护**：同一时刻仅允许一个进行中弹劾；跨过阈值瞬间用「条件更新 status 0→1，仅 rows==1 者执行换组长」做幂等闸门（沿用 settled 的模式）

## 二、数据模型（2张新表，样式对齐 duel_join_request）

- `duel_impeachment`：id、duel_id、initiator_id、reason varchar(20)、status tinyint（0进行中/1成功/2失败）、fail_reason varchar(64)（过期未过半/组长已变更/发起人已离局）、impeach_cnt int、maintain_cnt int（原子计数列，免 count 查询）、expire_time、finish_time、create_time；`index idx_duel_status (duel_id, status)`
- `duel_impeachment_vote`：id、impeachment_id、duel_id、user_id、vote tinyint（0维持/1弹劾）、create_time；`unique key uk_impeach_user (impeachment_id, user_id)` 一人一票由数据库兜底
- 建表语句追加到 `sql/create_table.sql` 并应用到本地 my_db；实体/Mapper 按 DuelJoinRequest 裸 BaseMapper 模式
- `DuelConstant` 增加：IMPEACH_STATUS_ACTIVE/SUCCESS/FAILED、VOTE_MAINTAIN=0/VOTE_IMPEACH=1、冷却与期限时长常量

## 三、接口（挂 DuelController，沿用 login-user + BaseResponse 风格）

- `POST /duel/{duelId}/impeach`：body `{reason}`，发起弹劾
- `POST /duel/{duelId}/impeachment/vote`：body `{impeachmentId, vote}`，投票
- 详情查询不加新端点：`GET /duel/{duelId}` 的 `DuelVO` 增加进行中弹劾概要 `impeachment`（发起人昵称/原因/弹劾数/维持数/基数/截止时间，viewer 无关，进 DuelAggData 60s 缓存 + 写时逐出）与个人字段 `myImpeachVote`（null未投/0维持/1弹劾，live 不缓存）；已结束的弹劾不再展示（留表审计）

## 四、代码落点

- **新服务** `DuelImpeachmentService(Impl)`：initiate / vote / resolveExpired（扫期+惰性）/ assembleVO；发起与投票/换组长用 transactionTemplate
- **DuelServiceImpl 两处钩子**：
  - `transfer`（让渡）：让渡成功时若有进行中弹劾 → 自动失败（fail_reason=组长已变更）——弹劾对象已换人
  - `removeMember`：进行中弹劾的发起人**禁止被移除**（防组长移人掐死弹劾）
  - 成功结算前复核发起人仍是正式成员（极端并发兜底，否则按失败结算）
- **DuelScheduler**：新增 `@Scheduled(cron = "0 */10 * * * ?")` 扫期任务，结算过期弹劾
- **投票流程（事务内）**：校验成员/期限 → 插票（唯一键防重，撞键报"已投过票"）→ 条件更新计数列 cnt=cnt+1 → 重读计数，若 impeach_cnt×2 > member_count → 条件更新 0→1 抢占成功资格 → 换 leaderId + finish_time → 逐出聚合缓存

## 五、冒烟计划

1. 发起护栏：招募中拒、组长发起拒、非成员拒、已有进行中弹劾拒；3人局发起成功后 impeach_cnt=1
2. 投票：成员分别投弹劾/维持计数正确；重复投票被拒；SQL 手改 expire_time 到过去后投票被拒
3. 成功：3人局第2张弹劾票投出瞬间 leaderId 换人、老组长 myRole=member、status=1；重复触发不再换人（幂等）
4. 失败-到期：手改 expire_time 触发扫期 → status=2；冷却期内再发起被拒，把 finish_time 拨到24h外后可再发起
5. 护栏：进行中弹劾时移除发起人被拒；组长让渡后弹劾自动失败（fail_reason=组长已变更）
6. 资金零断言：全程钱包余额与 coin_transaction 无任何变动；duel.member_count 不变

## 六、实现顺序

建表+实体 → 常量 → 服务（发起/投票/结算）→ 控制器+VO 装配 → transfer/removeMember 钩子 → 调度 → 冒烟 → 提交（完成后按惯例归档设计文档）

## 七、明确不做

弹劾历史列表与逐票明细公开（仅聚合计数）、投票提醒推送（前端轮询详情即可）、弹劾成功二次确认、发起人申诉
