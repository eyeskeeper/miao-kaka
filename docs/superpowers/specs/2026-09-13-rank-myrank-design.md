# 喵卡卡 · 连击排行榜附加当前用户排名（myRank）设计文档

日期：2026-09-13
状态：已实现并通过三分支冒烟（提交 `d827518`）
前置：一期排行榜、Redis 缓存（`2026-09-12-redis-cache-design.md`）

## 1. 需求

`GET /rank/streak` 除 Top 50 列表外，同时返回当前用户的排名 `myRank`——用户不必翻榜找自己，尤其是 50 名之外的用户。

## 2. 设计

**响应升级**：`BaseResponse<List<RankItemVO>>` → `BaseResponse<RankBoardVO>`，其中 `RankBoardVO{list, myRank}`。`list` 保持原条目结构；注意这是**响应结构变更**（裸数组 → 包装对象），前端联调需知。

**排名口径与榜单完全一致**：连击降序、id 升序（同分按加入先后）、排除封禁用户。三分支：

| 分支 | 取值方式 | 成本 |
|---|---|---|
| 当前用户在 Top 50 内 | 直接取榜单条目的名次 | 零额外查询（命中榜单缓存） |
| 连击 > 0 但在 50 外 | 实时补算：`1 + COUNT(连击更高 OR 连击相同且 id 更小)`（同口径、排除封禁） | 一次索引 COUNT |
| 零连击 | `myRank = null`（暂无排名） | 无 |

榜单 Top 50 部分照旧走 5 分钟 Redis 缓存；**榜外补算刻意不缓存**——保证"我的名次"始终反映当前数据，且该查询为用户个人数据、跨用户命中率不划算。

已知可接受的不一致：缓存 TTL 窗口内（≤5min）"我的名次"（实时）与榜单条目（缓存）可能相差最多一个名次的写入延迟，均为展示性数据。

## 3. 验收记录（2026-09-13，三分支全通过）

| 分支 | 场景 | 结果 |
|---|---|---|
| 50 外 | 55 个假人（连击 99~45）压制下、连击 1 的真实用户 | `myRank=56`（count 55 + 1）✅ |
| Top 50 内 | 连击 45 的用户（榜上第 55 位） | `myRank=55`（取榜单名次）✅ |
| 零连击 | 无任何打卡的用户 | `myRank=null` ✅ |
| 清理 | 55 个假人已全部删除 | ✅ |

## 4. 过程记录

1. 验证"榜内分支"时设计了一组假人数据，其连击公式为 `100-n`（n=1..55）——最初误以为 `rank_dummy55` 连击是 99，实测 55 后才发现公式指向 45、榜上恰排第 55。两个分支在数据一致时结果相同，区分它们靠的是取值路径（榜单名次 vs count 补算），不是数值差异
2. 排行榜缓存的陈旧窗口（≤5min）与实时补算并存属预期行为，二期若有强一致诉求可改为写时逐出携带 myRank 重算
