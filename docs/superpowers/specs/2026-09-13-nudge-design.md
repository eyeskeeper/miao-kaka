# 喵卡卡 · 拍一拍（组内提醒打卡）设计与验收文档

日期：2026-09-13
状态：已实现并通过全链路冒烟（提交 `4e268d7`）
前置：二期死斗模式（`2026-09-11-duel-and-focus-design.md`）、Redis 基建（`2026-09-12-redis-cache-design.md`）

## 1. 需求

小组（一期即死斗挑战）内成员可以提醒其他成员打卡：用户 A 选择同组成员 B"拍一下"，B 收到一条由 A 预先编辑好文案的提醒消息。**核心约束：拍一拍行为与消息不落数据库表。**

## 2. 决策记录（grilling 两轮收敛）

| 决策点 | 结论 | 备注 |
|---|---|---|
| 消息落点 | Redis List，**当日过期**（北京时间 24 点） | 初提 7 天 TTL，用户纠正："当日提醒无需长生命周期"；与频控重置同一时刻，语义统一 |
| 推送方式 | **轮询**（`GET /nudge/mine` 读取即消费） | WebSocket 曾被提出并评估（混合模式：在线推+离线 Redis 兜底），用户决定一期不引，二期"到点提醒推送"时再升级 |
| 模板存储 | **入库**：`user` 表加列 `nudge_text varchar(20)` | 用户主动推翻最初"完全不碰库"的表述——最终边界：**模板入库，行为与消息不落表** |
| 文案链 | 两级：A 的模板 → 系统默认"戳了戳你，快去打卡！" | 用户明确拍一拍是随手动作，**无请求体文本**（对比最初"三级链"设计删掉了即时文本） |
| 频控 | 发起方**每日限 5 次**（不分对象） | 用户否决了"A→B 每日 3 次"的按对限法；北京时间 24 点重置 |
| 收件箱 | 上限 20 条，满则拒收 | 读取即消费，无已读状态机 |
| 内容边界 | 仅长度 ≤20 字，不做内容审核 | |
| 资格 | A≠B；双方均为该死斗成员且非退出态（QUIT） | 离队成员不可拍、不可被拍 |

## 3. 存储设计

| 内容 | 位置 | key / 列 | 生命周期 |
|---|---|---|---|
| A 的模板文案 | MySQL `user.nudge_text` | 可空；空=用系统默认 | 永久 |
| 拍一拍消息（JSON：发送者/文案/时间） | Redis List `miaokaka:nudge:inbox:{B}` | RPUSH + 每次刷新 TTL 至当日午夜 | 当日 24 点整过期 |
| 发起方当日计数 | Redis 计数器 `miaokaka:nudge:cnt:{A}:{yyyyMMdd}` | INCR + TTL 至午夜 | 当日 24 点过期 |

校验顺序细节：**先查收件箱容量、后耗发送额度**——投递失败不扣发起方的每日次数。

## 4. 接口契约（4 个）

- `PUT /nudge/template` — 编辑我的文案（≤20 字，空串=清除恢复默认）
- `GET /nudge/template` — 返回 `{nudgeText 已存值, effectiveText 实际生效文案}`
- `POST /duel/{duelId}/nudge/{targetUserId}` — 拍一下，返回 `{toUserId, text 实际发出文案, dailyRemaining 今日剩余次数}`
- `GET /nudge/mine` — 读取即消费，返回 `{count, items[{fromUserId, fromUserName, text, time}]}`

## 5. 实现要点

- `CacheService` 新增 List/计数器原子操作（`increment`/`listSize`/`listPush`/`listRange`）。**降级语义与缓存刻意不同**：缓存故障静默回源；此处 Redis 是数据本身，故障返回 null，服务层转译为友好"提醒功能暂不可用"——绝不静默吞掉消息
- Redis 不可用时功能整体不可用（模板编辑不受影响，它走 DB），符合"消息宁可不可发、不可丢"
- `nudge` 未建实体/Mapper/Service 数据层——全功能仅 `NudgeServiceImpl` 一个类 + 常量类，无任何数据库表
- 模板保存后逐出 `miaokaka:user:{id}` 登录态缓存（用户行变更纪律）

## 6. 验收记录（2026-09-13，Redis 在线，全部通过）

| 验收项 | 结果 |
|---|---|
| 投递与模板链 | A 存模板 → B 收到模板文案；无模板用户 → B 收到系统默认（20 条全覆盖） |
| 读取即消费 | 首读返回全部并清空；再读 0 条 |
| 日限 5 次 | `dailyRemaining` 4→3→2→1→0，第 6 次精确拒绝"今日拍一拍次数已用完（每天 5 次）" |
| 收件箱上限 20 | 5 成员灌箱：恰好停在 20，第 21 次精确拒收"对方的提醒箱已满，稍后再拍吧" |
| 资格校验 | 拍自己 40000；非成员 40300"你不是该死斗的正式成员" |
| 加入锁联动 | lazy 开赛触发后，未加入者被"该死斗已开始"锁定（与死斗规则一致） |
| Redis 故障降级 | （前一日 Redis 停机时实测）模板编辑照常；拍一拍/收件箱友好报"暂不可用"，无静默丢消息 |

## 7. 过程记录

1. **测试脚本假象**：压测时"28 次全过、上限未触发"——根因是验证脚本 `grep -q "0"` 会匹配 `"code":50001` 中的字符 0，把拒绝响应当成功。修正匹配（`"code":0,` 精确匹配）后，拒绝次数与收件箱条数完全吻合设计。应用代码无问题
2. **端点位置修正**：拍一拍最初误挂在 `/nudge/duel/...`，与共识清单 `POST /duel/{id}/nudge/{target}` 不符，已移入 `DuelController`
3. **开赛锁联动**：灌箱压测时新成员加入被拒——不是 bug，是加入动作触发的 lazy 开赛使死斗进入进行中状态；测试用 SQL 拨回招募态继续
