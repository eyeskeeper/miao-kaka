# 喵卡卡 · 用户管理系统 + 组长能力扩展（含押金"每日即退"重构）设计文档

日期：2026-09-15
状态：已实现并通过全链路数值断言冒烟（提交见 git log；测试 9/9 绿）
前置：死斗模式（`2026-09-11-duel-and-focus-design.md`）、缓存基建（`2026-09-12-redis-cache-design.md`）

## 1. 需求

①管理员对任意用户增删改查；②组长能力扩展：删除成员、接受成员加入申请、让渡组长身份（审核打卡一期已完成）。其中"组长移除进行中成员"触发了押金公式的模型级重构。

## 2. 决策记录（grilling 两轮 + 一次口径澄清）

| 决策点 | 结论 |
|---|---|
| 管理员"增" | 运营手动开号：账号 + 初始密码（BCrypt）+ 昵称；赠 1000 喵币与注册一致 |
| 管理员"删" | 三护栏：不能删自己与其他 admin；名下存在招募中/进行中死斗成员身份（含押金）→ 拒绝；逻辑删除 + 账号归档改名 `{账号}#del{id}` 释放原账号名。封禁保留（可逆惩罚 vs 清除，并存） |
| 管理员"改" | 昵称/头像/角色（user↔admin，禁改 ban）/密码重置；账号不可改 |
| 组长移除成员时机 | 用户决策：**进行中也可移除**——为此押金公式改为"按人数动态计算"（见第 3 节）；招募中移除=全额退款 |
| 申请制加入 | 每死斗 `joinMode` 开关（0 自由=默认 / 1 审批）；审批模式：申请不扣押金，**批准时才扣**，余额不足自动拒绝留痕；开赛时待审申请自动拒绝（未扣款零成本） |
| 让渡组长 | 目标须为正式成员（非退出/非移除）；招募中与进行中均可；即时生效，原组长降为普通成员 |
| 打卡审核 | 沿用（已完成） |

## 3. 经济模型重构：每日即退（本次核心）

原模型：押金全程托管，结束时按 `押金×D/T` 一次结算。新模型改为**流式**：

1. **每日即退**：凭证审核通过当天 → 立即退当日份额 `floor(押金/T)`（钱包流水新类型 `5: 每日退还`），`duel_member.refunded` 累计
2. **进行中移除**：移除退款 = `押金 × 剩余天数 / T`（用户给的公式）；罚没 = `押金 − 已退 − 移除退款`（即缺勤天份额）→ 入 `duel.removed_pool`
3. **最终结算（剩余成员）**：`end_refund = floor(押金×D/T) − refunded`（补齐舍入尾差）；罚没 = `押金 − refunded − end_refund`；总奖池 = Σ成员罚没 + removed_pool → `SettlementCalculator.splitByDays` 按剩余成员天数占比分配，余数沉没
4. 已移除成员状态 `4:已移除`，影子计划下架，最终结算跳过（其在移除时已即时结清）

**示例（T=7、押金 100，每日退 14）**：C 第 3 天被移除、出勤 2 天、已退 28 → 移除退款 = 100×4/7 = 57 → 罚没 15 入池。结算时 B 出勤 1 天：end_refund = floor(100/7)−14 = 0；罚没 86；总池 = 86(C? 不——见冒烟) 按天数占比分给有出勤者。

## 4. 数据模型变更

- `duel`：+`join_mode tinyint`、+`removed_pool int`
- `duel_member`：+`refunded int`；状态枚举加 `4:已移除`
- 新表 `duel_join_request`（duel_id、user_id、status 0待审/1通过/2拒绝、审核备注/时间）
- 管理端不新增列（操作现有字段）

## 7. 过程记录

1. 结算口径重构涉及真钱逻辑，全部用**逐人钱包余额 + 流水 `balance_after` 对账**断言，而非只看接口 200
2. 冒烟两次踩"开赛日=今天 + 创建即 lazy 开赛"导致人数不足自动解散——设计行为正确，测试需"明日建、加人、SQL 拨回今日"
3. 移除公式分母经用户澄清为剩余天数比例（`押金×(T−E)/T`），并顺势把整个押金模型升级为每日即退——单一功能需求演化为模型重构的典型案例
