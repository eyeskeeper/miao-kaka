# 任务位图跨天清零（修复"次日一键完成全天打卡"）

- 日期：2026-09-20
- 状态：已实现并冒烟通过
- 关联：2026-09-11-task-toggle-design.md（任务勾选引擎）

## 一、问题

`check_in_plan.task_progress`（'0'/'1' 位图）是跨天持久的累积状态，打卡完成后**不清零**。由此推论并确认的隐性问题：

1. **刷打卡漏洞（严重）**：普通计划第 1 天勾满自动打卡后，第 2 天起冻结解除、位图仍是全 1 —— 任意一次 `done=true` 勾选（哪怕该位本来就是 '1'，位图一个字符都不变）都会立即重新满足 `countDone >= tasks.size()` → `doCheckInInTx` 自动打卡。一个 21 天×5 任务的计划，第 2 天起每天点一下即完成全天，连击/积分/猫事件照常结算
2. **前后端状态矛盾**：前端 `utils/taskState.ts` 按天缓存（新的一天 UI 从 0/3 显示），后端真相却是 3/3 —— 用户勾 1 项，响应却报"3 项全部完成且已自动打卡"

根因：位图是"累积态"，但每日任务的业务语义是"当日态"，两者之间缺跨天清零动作。

## 二、修复（方案一：打卡落定即清零）

`applyGrowthAndPoints` 末尾（`checkInPlanMapper.updateById(plan)` 前）追加：

```java
plan.setTaskProgress("");
plan.setCompletedTasks(0);
```

**单一插入点覆盖全部完成路径**（两条结算链路都汇聚于此）：

- 普通计划 `POST /check_in` 与勾满自动打卡（`doCheckInInTx`）
- 死斗凭证审核通过（`settleApprovedCheckIn` → `doSettleApprovedInTx`）

语义：打卡落定那一刻即开启次日的空白清单。补卡（makeup）不经过该函数，不影响当日进行中的勾选（保持原语义）。死斗结算末端直接置位的 `autoApprovePending` 无需处理（局已结束，影子计划位图不再有业务意义）。

## 三、冒烟结果

| # | 用例 | 结果 |
| --- | --- | --- |
| 1 | 2 任务计划勾 1 项：progress="10"、completed=1、无记录、不自动打卡 | ✓ |
| 2 | 部分进度直接普通打卡：记录生成 + 位图清零（[]/0） | ✓ |
| 3 | **漏洞闭合**：SQL 删今日记录模拟次日 → 勾第 1 项 → completed=1/2、autoChecked=false、allDone=false、无记录（修复前此处会直接自动打卡） | ✓ |
| 4 | 勾满第 2 项 → 自动打卡 + 位图再次清零，连击重算正确 | ✓ |
| 5 | 死斗链路：勾满 → 传凭证提示 → 上传 → 组长通过 → 影子计划位图清零、记录转正常、连击 1 | ✓ |

## 四、明确不做

位图按天存储的表结构改造、toggle 时惰性重置（需要 last_checkin_date）、补卡联动清零（保持当日勾选不受补历史影响）
