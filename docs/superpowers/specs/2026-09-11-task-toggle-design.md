# 喵卡卡 · 每日任务勾选（部分打卡）设计文档

日期：2026-09-11
状态：已实现并冒烟验证（提交 `377ea4e`）
前置：一期打卡引擎（`docs` 外约定见 CLAUDE.md）、二期死斗模式（`2026-09-11-duel-and-focus-design.md`）

## 1. 背景与问题

一个打卡计划可配置多条每日任务（如"喝一杯温水 / 拉伸 5 分钟 / 背 10 个单词"）。用户的每一次单项完成，交给前端还是后端记录？

## 2. 决策：后端记录每一次完成

沿用 10 分钟计时模式确立的判断原则，但结论相反：

| 场景 | 状态性质 | 结论 |
|---|---|---|
| 10 分钟倒计时 | 短暂一次性 UX 状态，丢失无损失，作弊无收益 | 前端 |
| 每日任务勾选 | **跨天、跨设备、可积累的持久状态**，丢失是体验硬伤 | **后端** |

作弊分析可直接翻篇：单项完成本身**没有任何奖励**——奖励（猫事件/经验/积分/连击）只在 `POST /check_in` 发放，已有唯一键与事件引擎把守。因此逐项记录是纯持久化问题，无需任何防作弊设计。

实现成本极低的另一个原因：一期建表时 `check_in_plan` 已预留 `daily_tasks`（任务名 JSON 数组）、`total_tasks`、`task_progress`（位图字符串，如 `"101"`）、`completed_tasks` 四个字段，本次只是启用它们。

## 3. 接口契约

`POST /plan/{planId}/task/toggle`，请求体：

```json
{ "taskIndex": 0, "done": true }
```

- `taskIndex`：0 基索引，对应 `daily_tasks` 数组顺序
- `done`：true=完成，false=取消完成

响应（`TaskToggleVO`）：

```json
{
  "planId": 4, "taskIndex": 0, "done": true,
  "taskProgress": "100", "completedTasks": 1, "totalTasks": 3,
  "allDone": false, "autoChecked": false,
  "checkInResult": null,
  "message": null
}
```

`allDone=true` 时 `autoChecked=true` 且 `checkInResult` 携带完整的打卡事件结算（猫攻击 BOSS/属性提升/暴击、经验积分、连击、AI 鼓励语）——**勾满最后一项即自动完成当日打卡**，用户少点一次，奖励即刻落地。

## 4. 实现要点

- `CheckInRecordService.toggleTask`（与打卡引擎同实现类）：事务内完成位图翻转与自动打卡（`transactionTemplate` 编程式事务，嵌套加入同一事务）；AI 鼓励语仍在**事务提交后**生成，不拖长事务
- 位图处理：按任务数补齐长度 → 翻转指定项 → 重新统计 `completed_tasks`；重复勾选幂等
- 未启用 `@Transactional` 代理，全部编程式事务，无自调用失效问题

## 5. 边界与规则

| 规则 | 行为 |
|---|---|
| 当日已有任意状态打卡记录（正常/待审核/异常） | 冻结勾选（数据已随打卡落定，再勾无意义） |
| 计划未配置每日任务 | 拒绝并提示直接打卡 |
| 下标越界 / 计划暂停 / 非本人计划 | 拒绝 |
| **死斗影子计划**（`plan_source=2`） | 勾选照常可用（仪式感），但勾满**不自动打卡**——提示走死斗凭证入口；押金比例只认审核通过的照片打卡 |
| 自动打卡与位图更新 | 同一事务：位图落库成功而打卡失败的中间态不可见 |

## 6. 冒烟记录（2026-09-11，全部通过）

三任务计划"晨间三件套"：

1. 勾 0 → `"100"`，1/3，不触发打卡 ✅
2. 勾 1 → `"110"`，2/3 ✅
3. 重复勾 1 → 幂等，仍 2/3 ✅
4. 勾 2 → `allDone=true, autoChecked=true`，猫"汤圆"攻击"内耗影魔"11 点伤害，+10 经验，DeepSeek 鼓励语实时生成 ✅
5. 打卡后再勾选 → 冻结拒绝 ✅
6. 打卡后再直接打卡 → 唯一键拒绝 ✅
7. 无任务计划勾选 / 下标越界 → 正确拒绝 ✅
